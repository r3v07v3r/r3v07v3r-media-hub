## Method

1. **Baseline.** All three TypeScript projects type-checked (the only error in a git worktree is the
   env-only missing `koffi` module), ESLint reported zero errors, and all 86 registered test files
   passed when run one by one.
2. **Candidate scan.** A grep-based scanner over `src/`, `daemon/`, `party-sync-worker/`,
   `scripts/`, `tests/` and the configs produced candidates: files with no importer, exported names
   that appear in no other file, CSS-module classes no importer reads, public assets nothing
   references, dependencies nothing imports.
3. **Documentation audit (workflow, 333 agents).** Seventeen finder agents each took one section of
   README.md, daemon/README.md, party-sync-worker/README.md, .ai/README.md, docs/ROADMAP.md,
   docs/remediation-proposals.md and the five design docs, enumerated every factual claim, and
   checked it against the code with path:line evidence; three more swept the IPC surface, the
   renderer surfaces and the build/platform surfaces for features the READMEs never mention. Two
   mappers built the playback chain and the service matrix from code alone. Every non-accurate
   finding, and a quarter of the "accurate" ones, then went to an adversarial verifier instructed to
   refute it; a refuted or low-confidence verdict escalated to a second verifier.
4. **Dead-code audit (workflow, 51 agents).** Every candidate from the scan was classified by an
   agent that read the defining file and grepped for indirect use (re-exports, string names,
   esbuild aliases, CSS access patterns, tests, scripts, workflows, electron-builder.yml). Every
   proposed deletion was then re-checked by a verifier that defaulted to "keep". Five structural
   candidates (the embed spike, the preview build, the AI review loop, the placeholder and artwork
   layers, the headless stubs) and two duplication sweeps ran alongside.
5. **Ranking (workflow, 15 agents).** Five judges with different lenses ranked the problems; the
   top five received a self-contained fix brief, each checked by a further agent against the code.
6. **Critic and re-check.** A completeness critic listed what the sweep missed (its points are
   folded into the READMEs and the lists below), and three verifiers re-checked the rewritten
   READMEs against the code before this change was finished.

Nothing was run live against TorBox, Jellyfin, the daemon or the relay. Claims that need a live
service to confirm were marked unverifiable and left as written where the code supports them.

## Behavioural defects found from the code

None of these were recorded anywhere before. Each has a fix brief below.

1. **The source gate runs before the cache tiers.** `stream:resolve` throws unless TorBox or an
   enabled Jellyfin is configured (`src/main/media-hub/torbox.ts:489-496`), and the renderer blocks
   earlier (`AppStateContext.tsx:1698-1707`). Both checks precede tier 1 (a complete local copy) and
   tier 2 (the paired daemon), so a fully cached title cannot play once TorBox is disconnected, and a
   household device that only pairs with the daemon cannot play at all.
2. **Anime never hits the r3-cache tier.** The feeder stores anime under `id::episode`
   (`src/shared/lancache/wantedList.ts:38-39`, empty season) while the resolver looks up
   `id:<season>:episode` (`torbox.ts:607-610`) and Kitsu episodes always carry a season
   (`core.ts:775`); the daemon matches exactly (`lanCache.ts:93`). Movies and series are fine.
3. **Remote sync drops failures for good, and two queues race.** `queueRemotePushes` is
   fire-and-forget and failures are only logged (`tracking.ts:165-214`); the pending queue holds
   only reconcile decisions; reconcile covers Simkl movies only. Separately, `watchlists.ts`
   re-implements the keyed serial queue (`planChangeChains`, lines 681-689) that `tracking.ts`
   already takes from `src/shared/media-hub/serialQueue.ts`, so a plan push and a history push for
   the same title are not ordered against each other.
4. **The Simkl episode fallback probably always fails.** `catalog.ts:840-846` calls
   `api.simkl.com/tv/episodes/<id>` without the `client_id` every other Simkl call adds; the error is
   swallowed and the degraded page shows no episodes. (Not verified live; the code path is clear.)

### 1. Make the tier-2 LAN-cache lookup use the feeder's anime content key

_Candidate C2. Effort S. Brief checked against the code by a second agent; the corrected version is shown._

The r3-cache feeder queues anime on the daemon under `kitsuId::episode`, with an empty season (src/shared/lancache/wantedList.ts:78-87, 117-124). The stream:resolve tier-2 lookup builds `catalogId:<season>:episode` by hand (src/main/media-hub/torbox.ts:607-609), and the renderer always sends a season for anime, so the exact-match lookup in src/main/media-hub/lanCache.ts:93 never finds anime the daemon holds. Add one exported builder, `lanCacheContentKey`, to src/shared/lancache/wantedList.ts that drops the season for anime, and use it in both the feeder and the resolver. Pin the behaviour with new assertions in tests/lanCacheFeeder.test.ts.

**Why it matters.** For anime, the r3-cache daemon's downloads and disk space are wasted. The feeder keeps asking the daemon to fetch the next anime episodes, but at play time the resolver looks under a different key (`kitsu:555:1:9` against the feeder's `kitsu:555::9`), finds nothing and falls through to TorBox. Nothing errors or logs, so in every anime session in a household with a paired daemon the cache server does nothing for a core content type. That fits the project note that the LAN tier has never been seen serving a playback. The fix is a key normalisation on the resolver side. Anime already queued on the daemon under `id::ep` becomes servable straight away, with no migration.
